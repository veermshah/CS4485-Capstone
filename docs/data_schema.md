# Data & Storage Schema

## 1. Purpose

This document defines the final source of truth for how FireLens stores, organizes, and shares data across the dashboard, VLM pipeline, evaluation page, chatbot, and backend API.

FireLens uses a file-based storage design instead of a traditional relational database for the final demo. Most of the application data is stored as static artifacts, including CSV files, GeoJSON files, image crops, source imagery, and evaluation outputs.

This schema covers:

- dataset metadata and master indexing
- building-level crop artifacts
- building metadata and GeoJSON footprints
- VLM prediction outputs
- evaluation results
- chatbot-accessible data
- live VLM evaluation inputs and outputs

---

## 2. Final Storage Model

For the final implementation, FireLens uses **Cloudflare R2 object storage** as the main data layer.

Cloudflare R2 stores:

- source pre/post-disaster imagery
- building-level crop images
- dataset index files
- evaluation outputs
- prediction artifacts
- GeoJSON building metadata

This design was chosen because the project is mostly file-driven and read-heavy. The dashboard, chatbot, and metrics page can read prepared artifacts directly instead of requiring a full production database.

---

## 3. Main Data Artifacts

### 3.1 Master Dataset Index

Canonical file:

```text
dataset_records.csv
```

Purpose:

- acts as the master index for the dataset
- connects each building ID with its tile ID, crop paths, bounding box, and ground-truth label
- is used by the dashboard, VLM pipeline, metrics page, and chatbot

Typical fields:

| Field | Type | Description |
|---|---|---|
| `uid` or `building_id` | string | Stable building-level identifier |
| `tile_id` | string / int | Source disaster tile identifier |
| `bbox` | object / string | Crop bounding box for the building |
| `pre_crop_path` | string | Path to the pre-disaster crop |
| `post_crop_path` | string | Path to the post-disaster crop |
| `label_gt` | string | Ground-truth xBD/FEMA damage label |
| `longitude` | float / null | Building longitude if available |
| `latitude` | float / null | Building latitude if available |

Notes:

- `dataset_records.csv` is the main lookup table for building-level data.
- It is generated by the image cropping/data pipeline.
- The frontend and chatbot should use this file as the main source for locating building records and crop images.

---

### 3.2 Building-Level Crops

Canonical folder:

```text
crops/
```

Typical structure:

```text
crops/<uid>/pre.png
crops/<uid>/post.png
```

Purpose:

- stores pre-disaster and post-disaster image crops for each building
- supports manual inspection in the dashboard detail panel
- provides input pairs for VLM inference
- supports the imagery tab in the UI

Notes:

- File extensions may vary, such as `.png` or `.jpg`.
- The stable part of the schema is the folder convention:
  - one building ID / UID
  - one pre-disaster crop
  - one post-disaster crop

---

### 3.3 Source Imagery / Map Tiles

Canonical folders may include:

```text
images/
tiles/
```

Purpose:

- stores source pre/post-disaster imagery
- supports raster slippy tile rendering in the map
- allows the frontend to show pre-disaster, post-disaster, and base map layers

Tile format:

```text
/{z}/{x}/{y}
```

Notes:

- The frontend uses Mapbox GL for map rendering.
- Custom pre/post imagery is served as raster slippy tiles.
- Source imagery and generated map-ready tiles are cached to improve performance.

---

### 3.4 Building GeoJSON

Recommended canonical file:

```text
buildings.geojson
```

or:

```text
buildings/buildings.geojson
```

Purpose:

- stores building footprint geometry
- allows the dashboard to render building overlay layers
- supports color-coding by damage class
- links visible buildings on the map to the building list and detail panel

Typical GeoJSON feature properties:

| Field | Type | Description |
|---|---|---|
| `building_id` or `uid` | string | Stable building identifier |
| `tile_id` | string / int | Source tile identifier |
| `damage_class` | string / null | Predicted or ground-truth damage class |
| `label_gt` | string / null | Ground-truth xBD/FEMA label |
| `gemini_label` | string / null | Gemini VLM prediction |
| `address` | string / null | Reverse geocoded address |
| `city` | string / null | City or place |
| `state` | string / null | State / region |
| `postal_code` | string / null | Postal code |
| `longitude` | float / null | Longitude |
| `latitude` | float / null | Latitude |

Geometry example:

```json
{
  "type": "Polygon",
  "coordinates": []
}
```

## 4. Logical Data Objects

Even though the final implementation is storage-based, FireLens still defines logical data objects to keep the system consistent.

---

### 4.1 Building Object

Represents one building footprint and its metadata.

```json
{
  "building_id": "81d57773-536e-4c5e-a283-649fabf5580a",
  "tile_id": "00000089",
  "event_name": "xview2_santa_rosa_wildfire_2017",
  "geometry": {
    "type": "Polygon",
    "coordinates": []
  },
  "address": "3853 Crestview Drive, Santa Rosa, California 95403, United States",
  "city": "Santa Rosa",
  "state": "California",
  "postal_code": "95403",
  "country": "United States",
  "longitude": -122.745904,
  "latitude": 38.483092
}
```

Required fields:

- `building_id` or `uid`
- `tile_id`
- `geometry`

Optional fields:

- `address`
- `city`
- `state`
- `postal_code`
- `country`
- `longitude`
- `latitude`

---

### 4.2 Prediction Object

Represents one VLM prediction for one building.

```json
{
  "building_id": "81d57773-536e-4c5e-a283-649fabf5580a",
  "run_id": "run_final_demo",
  "model_version": "gemini-2.5-flash",
  "damage_class": "destroyed",
  "confidence": 0.82,
  "reasoning": "The post-disaster crop shows severe structural damage compared to the pre-disaster crop.",
  "pre_image_url": "https://<r2-public-url>/crops/<uid>/pre.png",
  "post_image_url": "https://<r2-public-url>/crops/<uid>/post.png",
  "created_at": "2026-05-14T00:00:00Z"
}
```

Damage classes:

- `no-damage`
- `minor-damage`
- `major-damage`
- `destroyed`

Notes:

- Prediction results may come from offline batch inference or live evaluation.
- The dashboard mainly uses offline prediction outputs for stability.
- The Evaluate page can call the backend for live single-pair inference.

---

### 4.3 Evaluation Result Object

Represents one comparison between ground truth and Gemini prediction.

Canonical file:

```text
evaluation_results.csv
```

Typical fields:

| Field | Type | Description |
|---|---|---|
| `uid` or `building_id` | string | Stable building identifier |
| `true_label` | string | Ground-truth xBD/FEMA label |
| `gemini_label` | string | Gemini predicted label |
| `correct` | boolean | Whether prediction matches ground truth |
| `run_id` | string / null | Inference run identifier |
| `model_version` | string / null | Gemini model version |

Example row:

```csv
uid,true_label,gemini_label,correct
81d57773-536e-4c5e-a283-649fabf5580a,destroyed,destroyed,true
```

Purpose:

- powers the metrics page
- supports confusion matrix generation
- supports per-class precision, recall, and F1 metrics
- gives chatbot access to model performance data

---

### 4.4 Run Object

Represents one model run or evaluation batch.

```json
{
  "run_id": "run_final_demo",
  "model_version": "gemini-2.5-flash",
  "data_version": "xview2_santa_rosa_final",
  "started_at": "2026-05-14T00:00:00Z",
  "finished_at": "2026-05-14T02:00:00Z",
  "notes": "Final batch inference for FireLens demo"
}
```

Purpose:

- supports reproducibility
- records which model and dataset version produced the results
- helps connect predictions and evaluation metrics to a specific run

---

## 5. Chatbot Data Access

The chatbot does not run the VLM for every question in the final dashboard workflow.

Instead, it reads from the same prepared artifacts as the dashboard:

- `evaluation_results.csv`
- `dataset_records.csv`
- building GeoJSON / metadata
- damage labels
- prediction results
- geospatial context from selected or visible buildings

The chatbot can answer questions such as:

- where severe damage is concentrated
- which buildings are likely unsafe
- false positives and false negatives
- comparison between Gemini predictions and ground truth
- summaries for selected map areas or neighborhoods

The chatbot uses the same data sources as the dashboard to keep responses consistent with what users see on the map.

## 6. VLM Data Flow

FireLens supports two VLM workflows.

---

### 6.1 Offline Batch Inference

Used for the main dashboard, metrics page, and chatbot.

Workflow:

1. Load building-level pre/post crop pairs.
2. Send each image pair to Gemini.
3. Receive structured JSON output.
4. Save prediction label, confidence, and reasoning.
5. Write results into `evaluation_results.csv` or prediction output files.
6. Dashboard, metrics page, and chatbot read from the stored outputs.

This design avoids repeated live inference for every building and reduces cost, latency, and API rate-limit issues.

---

### 6.2 Live Single-Pair Evaluation

Used by the Evaluate page.

Workflow:

1. User uploads one pre-disaster image.
2. User uploads one post-disaster image.
3. Frontend sends the pair to the FastAPI backend.
4. Backend calls the Gemini API.
5. Gemini returns:
   - predicted damage label
   - confidence score
   - reasoning
   - model name
6. Frontend displays the result to the user.

This workflow is used to demonstrate that the VLM model can be tested directly.

## 7. Metrics Schema

The metrics page uses `evaluation_results.csv` to compute and display:

- total buildings evaluated
- overall exact-match accuracy
- aggregate precision
- aggregate recall
- aggregate F1 score
- confusion matrix
- per-class support
- per-class precision
- per-class recall
- per-class F1

Final reported values:

| Metric | Value |
|---|---|
| Total buildings evaluated | 4,226 |
| Overall accuracy | 81.35% |
| Aggregate precision | 39.47% |
| Aggregate recall | 34.84% |
| Aggregate F1 | 36.37% |

Notes:

- Unclassified samples are handled separately.
- Accuracy alone is not enough because the dataset is imbalanced.
- No-damage and destroyed are stronger classes.
- Minor-damage and major-damage are harder due to low support and subtle visual differences.

## 8. Deployment Data Configuration

### Frontend

The frontend is deployed on Vercel and can also be run locally from the `client/` folder.

It requires environment variables for:

- Cloudflare R2 public/base URL
- Mapbox API key
- backend API URL

Example variable names:

```env
FIRELENS_DATA_BASE_URL=https://your-r2-public-url.example/
NEXT_PUBLIC_MAPBOX_TOKEN=your_mapbox_token_here
NEXT_PUBLIC_BACKEND_URL=http://localhost:8000/
BACKEND_URL=http://localhost:8000/
```

### Backend

The backend is deployed on Render using FastAPI. For local development, it runs from the `backend/` folder on port `8000`.

Backend local setup requires a `backend/.env` file.

Example:

```env
ALLOWED_ORIGINS=http://localhost:3000/
PUBLIC_BASE_URL=http://localhost:3000/
GEMINI_API_KEY=your_gemini_api_key_here
SEARCH_PROVIDER=brave
SEARCH_API_KEY=your_brave_search_api_key_here
```
Variable descriptions:

| Variable | Purpose |
|---|---|
| `ALLOWED_ORIGINS` | Allows the local frontend to call the backend |
| `PUBLIC_BASE_URL` | Base URL used by the backend for local app references |
| `GEMINI_API_KEY` | Required for Gemini VLM and chatbot requests |
| `SEARCH_PROVIDER` | Search provider used for external disaster-related references |
| `SEARCH_API_KEY` | API key for the configured search provider |

## 9. Definition of Done

The data schema is complete when:

- `dataset_records.csv` exists and is up to date
- `evaluation_results.csv` exists and matches the final Gemini run
- building crops are available under the stable `crops/` structure
- building GeoJSON / metadata can be loaded by the dashboard
- frontend, chatbot, metrics page, and backend use consistent identifiers
- damage labels use the same four xView2 classes
- live VLM evaluation can accept one pre/post image pair
- documentation explains where data lives and how it is consumed

---

## 10. Future Extension

A future production version may replace the storage-first approach with a relational database such as PostgreSQL or Supabase.

Possible future tables:

- `buildings`
- `runs`
- `predictions`
- `evaluation_metrics`
- `flagged_buildings`

However, for the final course project, the authoritative implementation is the Cloudflare R2 + CSV/GeoJSON storage model.
